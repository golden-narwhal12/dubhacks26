# Local execution

`desktop/toolchain.ts` compiles validated project firmware with the installed Arduino CLI. It supports Mega 2560 Rev3 (`arduino:avr:mega:cpu=atmega2560`) and Espressif ESP32-S3-DevKitC-1 v1.1 (`esp32:esp32:esp32s3`). ESP32 defaults are 4 MB flash, no PSRAM; the actual module variant still needs confirmation before a physical operation. Compilation and simulation never access physical devices; the separate approved hardware service handles upload and serial access.

The first `.ino` file (preferring `sketch.ino`) becomes `sketch/sketch.ino`; other files retain validated simple names. Duplicate names, including case-only duplicates, are rejected. Files and compiler outputs live in a private temporary directory, deleted after the result. Compiler arguments and supported board targets are fixed; no shell or model-provided build flags are accepted. A generated Arduino CLI configuration redirects user libraries, downloads and build cache to scratch, while reading installed board packages from the standard macOS Arduino15 directory. Existing user libraries/custom data directories are not implicitly supported. HOME is preserved. Output is limited to 64 KiB per process, compile time to 120 seconds, and simulation to a 3-second wall-time sample. Stop/cancel terminates the subprocess group, including compiler children, with forced termination after 500 ms if necessary. Returned results carry the compiled project revision.

On macOS both compiler and simulator run under a generated `sandbox-exec` profile inherited by child processes. It denies network I/O and regular-file contents outside explicit system/SDK/tool/package/index/scratch roots, and denies writes outside scratch/device streams. It allows filesystem metadata, inherited pipes and other required macOS runtime operations; broad system roots remain readable. This is targeted confinement rather than a complete hostile-native-code sandbox. Missing/unsupported confinement fails closed; no unrestricted build fallback. Tests use synthetic excluded files and a loopback connection attempt, never user secrets.

## Simulator setup

Run `node scripts/setup-simavr.mjs`. It requires Git, make, clang/Xcode command-line tools and network access for the initial source download. It builds pinned upstream simavr commit `5b08da60497f7564f50941f74a549fe2851db030` under ignored `artifacts/tools`, retaining the source, license and build metadata. No system installation is needed. The standalone executable is GPL-3.0-or-later; it is spawned externally, not linked into Electron. Packaging includes the prepared simulator with its license and corresponding source archive.

This build intentionally disables libelf/libdwarf and loads the compiler's Intel HEX output. The [official build files](https://github.com/buserror/simavr/blob/master/Makefile.common) permit a source-tree executable without system installation. The [upstream simulator](https://github.com/buserror/simavr) lists ATmega2560, UART and GPIO support, while describing support for AVR parts above 128 KB flash as preliminary. That limitation remains visible in the full simulation log. When available, `npm run package` includes the standalone helper, license, pinned source metadata and corresponding source archive in the local app bundle; it is not linked into Electron.

The simulation runs compiled ATmega2560 instructions at a configured 16 MHz. It captures actual emulated UART output and digital GPIO transitions for up to sixteen explicitly bound Mega signals, using documented package port/bit identities. Wall time and emulated time differ. It does not execute ESP32-S3 firmware or simulate the external LED, resistor, physical wiring, supply/current, or analog networks. A successful sample means the bounded MCU execution completed; it does not certify circuit correctness.

## Verification

`npx vitest run tests/toolchain.test.ts` verifies cancellation, subprocess timeout/output limits, literal argument passing, unsafe-path rejection and explicit ESP32 simulation unavailability. `TRACE_LIVE_TOOLCHAIN=1 npx vitest run tests/toolchain.test.ts` additionally compiles both requested board targets and executes the Mega example. These live checks require installed cores and simavr; they are opt-in rather than silently passing with mocks.

Observed on macOS arm64, 2026-10-17: Arduino CLI 1.5.1, AVR core 1.8.8, ESP32 core 3.3.11. All ten checks passed, including synthetic confinement checks. The Mega example compiled to 2,778 flash bytes and 238 SRAM bytes. The actual execution printed `Trace: indicator ready`, alternating `indicator ON` / `indicator OFF`, and recorded 73 digital transition samples on PB7 / documented D13 during one 3-second wall-time run. The transition count varies with host speed and is not a deterministic timing assertion. Both Mega and ESP32 builds succeeded. No physical board was involved.

## Physical operations and serial

Prototype → Verify runs local rules plus compilation. Program Board requires an explicit project target and detected serial port. Missing/stale verification offers Cancel / Verify / Program Anyway; Verify never uploads afterward. Compilation cannot be bypassed. Programming prepares exact visible source/configuration and displays the immutable artifact before approval. It stops monitoring, invokes fixed `arduino-cli upload --fqbn … --port … --input-dir …` arguments under a selected-device-only policy, and normally restarts the board. Success opens Debug; failure stays in context. Cancellation is best-effort and may leave device state unknown.

Mega defaults are unchanged. ESP32-S3 programming additionally requires user confirmation of flash and PSRAM settings matching the actual module. Upload/serial implementation is fixture-tested, **not yet real-device tested**. Do not present fixture output as hardware evidence.

Debug Start monitoring creates an explicit connection review. SerialPort opens exclusively; DTR/RTS are deasserted after open, but the driver/board can pulse lines during opening and cause a reset. This behavior has not been measured on the user's board. There is no automatic open on workspace navigation or reconnect to another device. A successful upload offers monitoring; only the explicit resume-after-upload option restores an existing known device/configuration. Reset requires an already connected monitor and uses a disclosed 100 ms DTR pulse. Serial transmit reviews exact text/hex bytes and line endings. No undocumented payload meaning is inferred.

Raw output persists while the app monitor session lives, independently of workspace layout. Buffers/history are bounded and dropped older lines counted. Mapping editor previews one selected example before saving. Supported formats are finite numeric `key=value` fields separated by whitespace/comma/semicolon, and JSON object dot paths. Duplicate key/value fields, null/missing/non-numeric values and malformed records do not become zero. Optional device timestamps remain separate from host receipt times. Units/measurement-versus-command meaning are explicitly declared by the mapping. No parser or firmware reporting is inserted during build/upload. Firmware export uses the same visible source bytes; dependencies are installed core libraries plus pinned official Servo1.3.0 when used; arbitrary user libraries remain excluded by confinement.

User-driven hardware verification: choose the actual Mega/port, review the sketch and wiring, run Verify, explicitly Program Board and approve the displayed artifact, then approve Start monitoring at the sketch's baud. Compare real raw output with mapped readings. Decline serial/reset requests unless the exact operation is desired. No developer physical test is authorized merely by this implementation task.

Serial driver callbacks are bounded to five seconds each. Cancellation abandons ownership and attempts to close; a driver that does not respond can delay actual OS release, so cleanup is best effort. Late open callbacks cannot reclaim the monitor. No operation is reported completed after its cancellation signal. Connection/reset/transmit approval also binds baud and line framing. Closing the macOS window does not itself quit the app; explicitly stop monitoring or quit to release the session.

## Servo dependency

Run `npm run setup:libraries` once before building/packaging servo projects. It downloads the official [Servo1.3.0 release](https://github.com/arduino-libraries/Servo/releases/tag/1.3.0), verifies SHA256 `d25b0d77f10a810d24876c570410f32cc3129f9cc3d0370c861a278b969b4b38`, and retains the unchanged library and license in the fixed tools root. The same dependency is bundled locally and recorded by sketch export. Install that version in Arduino IDE for equivalent compilation. Servo control remains visible user source; no automatic pulses/reporting helpers are injected. The new real confined toolchain run passed all11 checks, including a visible Servo.h sketch, Mega/ESP32 builds, emulation and confinement. No physical board was touched.

Latest follow-up: all 12 `npm run test:toolchain` checks passed, including the complete visible servo/encoder example with pinned Servo 1.3.0. The packaged app launched from `/private/tmp` and executed its bundled MCU helper. No upload/serial/reset/transmit occurred; compiler/emulator checks provide no external peripheral or mechanical verification.
